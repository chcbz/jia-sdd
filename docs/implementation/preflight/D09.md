## Scope

D09 adds a privileged operational plane for:

1. bounded MySQL-backed delivery/outbox/Inbox metrics;
2. exact-scope, payload-redacted DLQ metadata query;
3. broker redrive of an unchanged message;
4. approved manual reissue with a new transport identity;
5. immutable request/result audit.

It must not change task completion facts, edit command payloads, create a second transport path, or expose Rabbit/DLQ operations through normal Juyi Hall user APIs.

## Frozen distinction

### Broker redrive

- Source is an existing, validated DLQ message and its durable delivery/outbox/Inbox provenance.
- Preserve the exact `messageId`, raw wire bytes, SHA-256, command ID, delivery ID and active attempt.
- Allowed only when no durable disposition proves the message was already handled.
- Publish through the existing D03 confirmed/mandatory publisher and canonical D04 route.
- Never rebuild JSON from a DTO and never edit headers/body.

### Manual reissue

- Source is a durable delivery plus its current active outbox/Inbox lineage.
- Create a new message/event ID and next transport attempt while preserving the business `commandId` and canonical business bytes.
- Record immediate parent message ID, requester, distinct approver and bounded reason.
- Use the final D06 fenced reissue service; do not duplicate its CAS, lock order, expiry or provenance rules.
- Reject `SUCCEEDED`, expired/terminal-forbidden sources, stale active messages, cross-scope access, payload/hash drift and missing audit fields.

## Operational API and ACL

Use a separate internal/administrative controller and a dedicated authority such as:

```text
agent-command-ops-read
agent-command-ops-redrive
agent-command-ops-reissue
```

The service must then revalidate trusted exact tenant/client scope and the durable task/target identity. Wrong scope and absent records use the same non-enumerating response. Do not accept tenant/client/operator identity solely from request JSON.

Normal list/detail results are bounded, stable-order and payload-redacted. They may expose command/message references, task/target, status/disposition, attempt, retry/expiry and timestamps. They must not expose raw payload bytes, credentials, full headers, lease tokens/owners, or cross-scope existence.

## Immutable audit

`CORE_LOG` is request access logging and is not a sufficient structured immutable replay audit. D09 should add a dedicated append-only `agent_command_operation_audit` record, conditionally initialized with the M3 transport schema, containing at minimum:

- operation ID and operation type (`BROKER_REDRIVE` or `MANUAL_REISSUE`);
- exact tenant/client/task/target scope;
- command ID, source/new message IDs, delivery ID and attempt;
- wire hash, requester, approver, reason and ticket/reference;
- requested/completed timestamps, outcome and bounded error code;
- created-by identity and immutable created timestamp.

The audit row is not a transport fact and must not alter delivery outcome. Request audit must be durably written before the external Rabbit publish; final outcome is appended as a second immutable row or updated only under an explicit one-way pending-to-terminal CAS. No audit row may contain raw payload or credentials.

Adding this table is a P0 schema change: fresh/upgrade/repeat/drift isolated MySQL verification and flag-off zero table access are mandatory. Production DDL remains separately authorized.

## Metrics contract

MySQL facts are authoritative. Minimum meters/projections:

- `agent_command_delivery_total{status}`;
- `agent_command_ack_latency_seconds` from durable timestamps only;
- `agent_outbox_backlog` and `agent_outbox_oldest_age_seconds`;
- `agent_rabbit_publish_failure_total`;
- `agent_rabbit_dlq_count`;
- WAITING/SENT-unacknowledged due and expiry proximity;
- Inbox disposition/result counts;
- relay/recovery scan results and reconnect queue depth;
- redrive/reissue requested/succeeded/rejected/failed counts.

Do not put tenant/client/task/agent/message IDs into unbounded metric labels. Exact-scope detail belongs in the privileged query endpoint/audit, not Micrometer tags.

## Flags and infrastructure safety

- M3 flags all false: no operations controller/service, DB poller, broker client, topology probe or transport-table SQL.
- DB/MQ shadow: read-only metrics may be explicitly enabled only by a separate safe gate; redrive/reissue remain disabled.
- Redrive/reissue require dispatch canary/scoped state plus exact allowed scope.
- Query must not provision Rabbit topology or connect to default/host `5672` as a side effect.
- Tests use only isolated/random Rabbit and MySQL where needed; no host Rabbit/MySQL mutation.
