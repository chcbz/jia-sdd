## Frozen C01B architecture

### Root lock and transaction rule

1. Every mutation of an existing task must enter one REQUIRED Spring transaction and lock the scoped `agent_task_meta` row before any mutable child or identity row.
2. Task creation must reserve/insert the scoped root first, then append `TASK_CREATED` in the same transaction. Duplicate/no-op create produces no event.
3. Shared identity locks retain the B08 canonical unsigned UTF-8 byte ordering. B07 retains task/member -> identity/runtime -> thread/message ordering after the task-root lock.
4. B03/B04/B06 must not write a child first and let `AgentTaskEventWriter` acquire the root later. They must acquire the root before the business mutation; the writer's later root lock is a same-transaction re-entry.
5. Event append occurs only after the corresponding business mutation has succeeded, but before commit. Any append failure rolls back all business writes; outer rollback removes all events and event-version updates.
6. Existing WebSocket/scene notifications stay after-commit and are not a substitute for the persistent task event.

### Frozen event catalog additions

The C01 catalog remains valid and C01B adds only the names required by actual B03-B08 writes:

```text
TASK_ASSIGNED, TASK_STARTED, TASK_BLOCKED, TASK_ARCHIVED
MEMBER_WORKING, MEMBER_DONE, MEMBER_FAILED, MEMBER_LEFT
WORK_ITEM_BLOCKED, WORK_ITEM_FAILED, WORK_ITEM_CANCELLED
WORK_ITEM_LEASE_RENEWED, WORK_ITEM_LEASE_RELEASED
REQUEST_CREATED, REQUEST_ACKNOWLEDGED, REQUEST_RESOLVED,
REQUEST_REJECTED, REQUEST_CANCELLED
THREAD_CREATED, MESSAGE_POSTED
```

Aggregate labels add `thread` and `message`. Request creation maps `help -> HELP_REQUESTED`, `review -> REVIEW_REQUESTED`, and all other currently supported request types to `REQUEST_CREATED`. Task notes map to `PROGRESS_REPORTED`; the payload must not contain the note body.

### Deterministic multi-event ordering

| Mutation | Required persistent event order |
| --- | --- |
| member + work item transition | member event -> work-item event |
| legacy assign | `TASK_ASSIGNED` -> members sorted by canonical agent bytes -> work items sorted by work-item ID bytes |
| legacy report | member event -> work-item event -> task aggregate event only if aggregate state changed |
| result commit | `ARTIFACT_PUBLISHED` -> `WORK_ITEM_SUBMITTED` |
| first team message with implicit thread creation | `THREAD_CREATED` -> `MESSAGE_POSTED` |
| lease release | preserve B04 attempt consumption; append exactly one `WORK_ITEM_LEASE_RELEASED` whose `toStatus` is the committed `ready` or `failed`; do not append synonymous requeued/failed events |
| lease expiry | `WORK_ITEM_REQUEUED` or `WORK_ITEM_FAILED` according to the committed outcome |

Within repeated members/work items, sort by byte-exact canonical aggregate ID. A path must not emit two synonymous events for one aggregate mutation.

### Payload allowlist

Allowed payload keys are bounded metadata only:

- common: `fromStatus`, `toStatus`, `reasonCode`, `expectedVersion`, `resultVersion`, timestamps;
- member/work item: canonical IDs, role, attempt count, lease expiry (never the lease token);
- request: request ID/type, target type/canonical target ID, status, short reason code;
- artifact: artifact ID/type/version, visibility, SHA-256 and byte length (never inline content or storage credentials);
- thread/message: thread ID/type, conversation ID, message ID/type, sender canonical ID, content byte length and SHA-256 (never full message text);
- task note/progress: note ID/type, content byte length and SHA-256 (never full note text).

Forbidden in every event: lease tokens, cookies, authorization/API headers, credentials, private keys, full chat/note/request/artifact content, arbitrary request metadata blobs and unbounded child snapshots.

### Zero-event rule

The following outcomes allocate no event ID/version and insert no event row:

- ACL/scope rejection;
- expected-version or lease-token CAS conflict;
- invalid state transition or invalid persisted state;
- idempotent duplicate/no-op whose committed business state does not change;
- validation failure before mutation;
- any transaction that rolls back.

- below `maxAttempts`, committed status is `ready`;

- the new work-item-to-task-root lookup must use byte-exact comparisons and deterministic ordering;

This correction restores backward compatibility and narrows event semantics; it does not authorize unrelated B04 changes.
