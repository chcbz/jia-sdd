## 0. 用户工作空间优先，悬赏关联可选

最新补充设计见 `workspace-design.md`：用户先拥有自己的文件库，可在未创建悬赏时上传管理；对话、任务页和工作空间复用同一文件/成果版本。选择文件交给 Agent 时才绑定明确执行范围；无悬赏的对话执行也复用内部 task/run，不强迫用户填悬赏。下文 task/run 表示执行追踪，不表示上传必须先有悬赏。

## 1. 入口：按结果选任务，不先选 108 个角色

聚义厅以对话和统一文件上传为主入口，保留 **生成图片 / 修改图片 / 制作 PPT** 快捷起点，并支持上传已有 PPT、Word、PDF、Excel 请求读取与修改。同一自有 Agent 可以支持多个入口，不强制配置三位 Agent。沿用原任务/对话，系统给出有依据的目标建议，提交携带显式 `agentId`；不可执行时说明缺少模型/编辑能力/原图/文件输出权限，而不是接受后永远等待。

### 对话修改为主，不做在线编辑器

- 三个入口是对话的快捷起点，不要求用户离开对话填写完整任务表单；原图/资料可随对话提交，也可从个人空间选择精确版本。
- 用户预览后直接说“保留人物，把背景换成浅蓝色”或“把第三页精简，增加一页总结”，由 Agent 执行修改并交付新版本。
- 成果卡片提供预览、下载、历史版本和“继续修改”；后者将明确的 task、artifact/version 带入对话。多份成果或源版本不明确时先澄清，不仅靠最近一条聊天猜测。
- PPT 预览支持逐页查看，图片可放大/对照；预览是只读视图，不提供拖拽排版、文字直接编辑、画笔或蒙版编辑。
- 对话修改关联既有 rework/执行链路，展示处理中与新版本；聊天回复不替代成果保存或正式验收。下载的 PPT 正文可编辑是文件质量要求，不是网页编辑器需求。

原有地图和名册保持分流，不恢复 `/agent/active`。已有聊天可以进入同一任务流程，但聊天里出现“完成”不能直接把任务标为已交付。

## 2. 场景 A：生成图片

1. 用户描述画面与用途，可选风格、比例和需要呈现的文字；缺关键内容再澄清，不强制填写模型参数。
2. 显示本次使用的能力、可用输出选项和是否涉及外部模型调用。默认只生成用户请求的数量，不后台批量出图或隐藏多轮重试。
3. 真正调用具备生图能力的工具，关联 task/run/request；图片回传后验证可解码、尺寸/格式与请求一致，再保存为可信 artifact。
4. 展示预览与原文件下载。用户可“基于此图继续修改”，固定选中版本，不能隐式改到其他历史图。
5. 内容不符时明确要求修改；模型不能可靠实现的文字/细节如实说明，不能用成功文件状态代替视觉验收。

验收样例：用户要求一张指定用途、主体与比例的配图，实际得到满足要求的图片，并能在重新登录后下载。

## 3. 场景 B：修改图片

1. 上传原图或选择自己已有成果的精确版本，预览确认原图；只收到本地文件路径/图片名称不算获得原图。
2. 输入“改什么”和“保留什么”，如换背景并保留主体。首版文字指令即可，局部蒙版/复杂画布不是前置。
3. 执行必须把实际原图传给已验证支持编辑的工具；仅有文生图能力时标记不可编辑，不静默降级成独立生成。
4. 结果保存为新版本，保留源图、指令及派生关系；可并排/切换对照并下载。失败不能覆盖原图或伪报完成。
5. 后续修改绑定用户选择的版本。若结果不满足保留要求，作为需要修改/未验收处理，不承诺未验证的像素级不变。

验收样例：对授权提供的原图更换背景，用户确认主体及指定保留项未被错误改变；原图和修改版均可领取。

## 4. 场景 C：制作可下载 PPT

1. 用户提供主题、文字资料、关键数据/结论，可附自己的图片；说明用途/受众和页数偏好。
2. 支持粘贴文字、图片素材及已验证的 PPT/Word/PDF/Excel 附件读取，将资料用于制作 PPT；逐格式标明解析覆盖范围，读取不完整时说明，不静默遗漏。已有文件的直接修改见下节。
3. 资料不足时澄清或标“待补充”，不编造业绩、引用、品牌信息与数据。用户已提供完整结构时可直接制作，不强制多一轮大纲确认。
4. 需要澄清结构时先给可修改的大纲；确认后执行内容组织→排版→真实 `.pptx` 生成→检查→保存→预览/下载。
5. 原生正文可编辑，图片为正常嵌入素材；表格/图表按所支持模板生成，不用整页图片冒充可编辑 PPT。不以 `.pdf` 或 `.html` 代替 `.pptx`。
6. 生成后检查页面内容、中文显示、文本溢出/遮挡和图片丢失；保留逐页预览，实际目标办公软件的打开验证与预览分开记录。
7. 用户可以说“缩短第三页、换个风格、补一页总结”，针对固定上一版本生成新版；不要求首版网页内直接编辑幻灯片。

验收样例：从一份真实、授权材料生成汇报 PPT，下载后正常打开、可改正文、关键数据一致；要求修改某页后获得新版本且旧版仍在。

## 4.1 场景 D：上传已有文件，让 Agent 读取与修改（用户最新补充）

统一的是文件入口、权限、对话和交付链路，不假设不同格式共享同一种解析/编辑能力。用户自己的文件也属于输入范围，取消“只改系统生成 PPT、Word/PDF/Excel 一律后置”的建议。

| 类型 | 首版建议支持的读取与修改 | 交付与检查 |
| --- | --- | --- |
| PPT `.pptx` | 读取页序/正文/素材，修改指定页文案、增删页或按指令调整风格 | 新 `.pptx` 与逐页只读预览；检查指定修改、未修改页和可编辑正文 |
| Word `.docx` | 读取正文/标题/基础表格，润色段落、补充章节、修改指定内容 | 新 `.docx` 与只读内容/分页预览；检查段落、表格和要求保留的结构 |
| Excel `.xlsx` | 读取工作表、单元格及公式信息；按指令修改数据/公式、整理表格 | 新 `.xlsx` 与分工作表预览；检查目标单元格、公式及关联范围；不以未重算缓存值冒充重算结果 |
| 常规文本型 PDF `.pdf` | 读取文字/页面，按确认范围调整内容或页面，必要时通过中间格式重建 | 新 `.pdf` 与逐页预览；重建可能影响排版时执行前说明，未经确认不静默换格式或承诺原位无损修改 |

以上是待核实的支持目标，不是现有能力声明。`.doc/.xls/.ppt` 旧格式、扫描 PDF/OCR、加密文件、宏、嵌入对象及复杂排版的支持状态分别盘点；不足时明确原因和替代方式，不让用户以为已经完整读取。常规 PDF 的内容修改若尚未跑通，必须报告该项未完成，不能仅以摘要或拆页冒充。

流程：
1. 用户在工作空间或对话上传文件；先绑定认证 owner 和实际文件版本，允许尚无悬赏。选择交给 Agent 时再明确执行任务、输入与源版本，校验真实类型。上传成功、读取成功、修改成功分开显示。
2. Agent 读取可支持的内容，定位页码、段落或工作表/单元格；只针对歧义或有损转换澄清，不机械要求所有任务先确认大纲。多文件处理固定各输入版本，不能混入其他任务附件。
3. 区分“阅读/解释”和“修改文件”：仅阅读不强制制造交付件；用户要求修改时必须生成实际文件，不能只返回操作建议。文件内指令视为待处理内容，不因此扩大工具、网络或数据访问权限。
4. 默认同格式交付，保留原件，检查约定修改和保留项，附简短改动说明；需要转换格式或无法保留对象时先告知并取得确认。解析/转换不自动执行宏、脚本或外部链接。
5. 新版本自动保存，生成同版本的只读预览并提供下载。Word/PPT/PDF 可使用渲染预览，Excel 按工作表查看；预览若截断或仅覆盖部分内容必须显式标明。预览不是交付文件的替代品。
6. 用户在同一对话继续提出修改，携带明确源版本；未改范围按约定保留。权限、失败恢复、幂等、版本历史复用共同链路。预览失败应独立标明并保留已验证文件下载，不虚报预览成功，该格式完整验收仍待补齐。

## 5. 共用成果路径（优先复用）

`任务输入 → 确定目标/能力 → 明确授权的工具执行 → 文件生成/编辑 → 成果检查 → 可信上传/入库 → 预览与下载 → 修改/验收`

- 沿用现有 task/work item/run、binding、lease/CAS 与 artifact 唯一事实源，不建立第二套“聊天附件即已验收”台账。
- 原图/输入资料标记 input，用作素材，不因上传成功成为该 Agent 的交付成果。优先复用可安全隔离的附件设施；没有合适输入通道时单列最小新增。
- 每个成果最少关联 task/run/producer、artifact/version、文件名、media type、字节数、hash、生成时间；派生成果另关联源版本。模型/工具来源有可信数据再展示。
- 工作空间对已有输出只作统一查询/归档投影，内容和版本仍以既有 artifact 为事实源；未关联任务的原件采用 owner-scoped 输入语义，不伪造 producer。
- 输入与输出都按真实内容与支持格式校验；限制依据实际处理工具、存储及风险，不能随意发明大小阈值。浏览器不执行用户附件中的脚本/宏；首版 PPT 输出不带宏。
- 不让客户端传任意服务器路径、任意外部 URL 或任意 owner；短期下载地址过期后凭当前权限重新获取，不能因临时链接过期导致已保存成果丢失。
- 预览图、图片原件、PPT、原始素材、旧版本都遵循同一 task/owner scope；不在公开目录或日志暴露私有文件/凭据。
- 在下载字节校验、成果入库尚未完成时，只能显示“生成中/保存中”，不能“已交付”。Provider 返回临时地址不等于持久化成功。

## 6. 状态、重试和取消

用户可见阶段：待补材料/待授权 → 排队 → 生成或修改中 → 保存/检查中 → 可领取/待确认 → 已确认；异常展示原因和下一步。阶段是已有状态机的展示投影，不另建相互矛盾的任务终态。

- 使用明确 task/run/version 关联进度和成果。刷新后从服务端恢复，不靠浏览器内存保住任务。
- 同一提交重复点击/网络重试不得重复触发昂贵生成；输入发生变化是新 revision。幂等 receipt 与重试策略需按实际 Provider/工具能力设计。
- 工具已完成但保存失败时优先恢复保存；Provider 响应丢失、是否已执行未知时明确“结果待确认”，先查已有请求/产物，不能盲目重发并重复扣费。
- 取消要区分用户请求、Agent/Provider 已确认与仍可能产生费用，不能承诺撤回已发生用量。
- 慢请求只观测与给出继续等待/回来查看的选择；不得以任意性能 SLO 中断可用请求。

## 8. 成本、范围与能力声明

- 文本模型名不能证明生图/改图能力；PPT 需要实际文件生成工具，不能只会写提纲。
- 图片费用可能与实际模型支持的计价维度有关，不能直接套用旧的“四类文本 token”公式；使用真实、版本化可追溯来源，否则显示未知。此处不指定 Provider 或价格。
- 生成 PPT 不默认逐页调用生图；需要 AI 配图时单独显式选择并确认成本/外发边界。
- 默认自有 Agent/私有任务，外单、钱包、市场、计费智力值、技能自动总结都不成为首版前置。
- 本文是产品内能力的设计；不以本次开发助手工具、临时本机脚本或人工生成的文件冒充产品上线能力。

## 4. 实施切片合同：先限范围，再开发

上位候选为 `workspace-contract-v1.md`；其完整范围不等于全部进入 1.10。本版仅实现 UPLOAD 分支与用户端 `/agent/personal-workspace` 文件/版本/preview/usage/trash/restore/operation 接口。名称、响应、错误、CAS 和幂等沿该合同，不修改旧 `/agent/tasks/{taskId}/workspace` 含义。

- 不接 ARTIFACT、taskId 筛选、派生关系和执行路由。未开放筛选须明确报不支持，不能忽略条件后返回全列表；空 relations/derivation 表示本版上传无关联，不代表全站没有关系。
- `usage` 对本版从未授权或关联的上传条目返回真实空引用及服务端 impactRevision；不伪造旧成果的空引用。1.11 启用关联/授权时需补齐竞态回归后才能开放。
- 新逻辑记录至少包含文件条目、不可变版本和操作回执，owner scope 参与所有读写与唯一键；预览先为同步安全图片/文本，不建设文档转换队列。
- 提交顺序：私有暂存与内容校验→不可变对象→数据库事务提交文件/版本/回执及必要事件→readback。文件系统和 DB 不是跨介质原子事务，失败走对账，不能仅靠事务注解宣称字节与 DB 一致。
- 回执丢失后使用**原幂等键**重放原请求；已取得 operationId 才使用 operation 查询。页面保留按身份隔离的操作标识；刷新后若需重新选文件，清楚提示，不能默默创建新 key 当重试。未实现分块续传，不宣称断点续传。
- 用户取消仅取消本次传输/等待，不能保证服务端已回滚；恢复时查询/重放既有回执。存储中断或 DB 失败的恢复不得重复追加版本。
- CORS 覆盖实际入口的 `Idempotency-Key` / `If-Match`，以及 ETag / 下载名称等实际需要的响应头；无跨域部署则验证同源路径，不为方便放开任意 origin。
- 首版不执行附件内容，HTML/SVG 不作为主动页面渲染；Office/PDF 只是存取，不能触发宏、外部资源或模型调用。
