# 聚义厅 MVP 价值闭环重评估（2026-09-18）

状态：**已完成认证只读体验与发布基线代码核对；用户随后明确 MVP 应提供生图、改图、可下载 PPT，以及上传已有 PPT/Word/PDF/Excel 让 Agent 读取修改，本轮已据此更新业务目标。不是启动、上线或用户验收回执。**

业务规格：`specs/juyiting-creative-delivery-mvp/`。业务范围已明确，技术接线合同仍为 draft；此前只读证据保持原样，未新增真实生成验证。

## 1. 结论：不是等到某个版本号，而是先交付一件真正做得成的事

最新分期将原集中于 1.10.0 的范围拆成 **1.10 文件库 → 1.11 Word 实际交付 → 1.12 图片/PPT → 1.13 Excel/PDF 与完整 MVP**；不是先上完整模型/计费智力值/外单/技能自动总结。正式交付复用已有实现，补足接线与用户体验；完整治理后移 1.14，多 Agent 协作后移 1.15。详见 `docs/implementation/VERSION_PLAN_20260918.md`。本次只更新规划，不改变下文只读审计事实。

最小产品承诺：

> 用户描述画面、上传原图或提供演示材料，选一位确实具备对应能力的自己的 Agent；系统真实生图/改图/制作 PPT、反馈进度，把图片或 `.pptx` 保存为可领取的交付物；用户离开再回来仍能取到，并能要求修改、确认完成。全程不需要开发者进终端搬文件、改数据库或手工补状态。

**这比角色数量、地图精细度、模型分数或市场页面更接近用户收益。** 收益是减少起草、整理、追问和寻找结果的时间，而非“点得动更多按钮”。

### 修正上一轮判断

此前“1.11.0 才有正式交付，所以到 1.11.0 才是 MVP”的判断过于依赖旧路线图：

- 线上已经显示“正式交付”并能读取；发布基线已经包含提交、验收、要求修改和相关事务实现。
- 未证实的是普通用户与真实 Agent 是否能把这些零件连成完整路径，尤其是成果产生、回传、持久保存和可领取。
- 因此不能把整套 R2 从头排为新建，也不能认为发布一个版本号就自然得到 MVP。
- 最新排期中 1.10.0 只承担文件库，不再称 Agent MVP；1.12.0 对应最初图/PPT目标，1.13.0 对应扩展后的完整文件 MVP。仍须通过真实业务验收，不能按版本名推导完成。

## 4. MVP 先服务谁、帮他做什么

### 4.1 第一批用户：已有自己的 Agent 的个人/小团队负责人

先面向能够接入一位已授权 Agent、需要反复整理材料和产出文档的用户，做**受控试用**，不是“任意新用户注册即用的商业市场”。理由是本账号已经有身份、绑定、在线名册、聊天和任务数据，复用成本最低。

首次接入仍需有清晰的检查页：`未绑定 / 已绑定未连接 / 已连接但能力未知 / 可执行所选任务 / 需要用户补授权`。选定一个官方支持的接入方式，不让用户先在 108 个角色与大量部署选项里选择。

如果目标改为面向不懂部署的公众，**无需开发者介入的 Agent 开通/授权/失败恢复**必须升为 MVP 必需项；不能把后台人工配好测试账号称为公开自助 MVP。若受限于暂不修改客户端，只能明确做现有 Agent 用户的受控版。

### 4.2 用户已明确的目标场景（覆盖此前文本方案与仅系统内 PPT 修改建议）

此前“先做 Markdown 文稿/行动清单”的建议不再作为充分的 MVP 定义。用户要求的是能够实际使用的图片和 PPT 文件：

| 场景 | 用户输入 | 真正可用的结果 |
| --- | --- | --- |
| 生成图片 | 用途、画面要求，可见的风格/比例默认值 | 真实生成、可预览/下载的图片，可继续修改 |
| 修改图片 | 上传原图或选已有图的版本，说明改什么/保留什么 | 实际使用原图的修改版，原图保留，可对照/下载/再次修改 |
| 制作 PPT | 主题、材料、关键数据、受众与用途 | 可下载、正常打开、正文可编辑的 `.pptx`，可按意见生成新版 |

同一自有 Agent 可以具备多种工具，不要求先建三位 Agent 或团队。入口按“我要什么结果”组织，而不是先让用户在角色目录里猜能力。图片/PPT 生成及已有 Office/PDF 文件读取修改可以分批交付，部分成功须明确标注，不能等同整体 MVP 完成。

用户最新补充：统一上传已有 PPT、Word、PDF、Excel，让 Agent 读取并通过对话修改，交付预览与可下载的新文件。首版建议 `.pptx/.docx/.xlsx` 与常规文本型 PDF，按格式分别验证读取、修改、预览、导出；不是任意文件无损处理承诺。PPT 生成不默认为每页调用付费生图。缺数据先澄清/标待补充，不能编造资料。图片修改必须真的把原图交给编辑工具，不能静默退化为另生一张。

不新增自动视频发布、复杂在线编辑器、多 Agent 编排和完整市场作为前置。详细流程、验收和授权见 `specs/juyiting-creative-delivery-mvp/design.md`。

## 5. 真正必须补什么（按用户损失排序）

| 优先级/编号 | 必补内容 | 优先复用 | 完成的业务证据 |
| --- | --- | --- | --- |
| P0 M01 | **真实执行与就绪诊断**：明确哪个 Agent、哪条运行链、什么工具/材料/授权可用；命令已投递、已接收、实际执行分开显示 | canonical binding、现有 runtime/命令回执/会话 | 真实任务与真实 run 关联；缺能力/离线能说明并给下一步；不能把 ACK 当完成 |
| P0 M02 | **任务输入与交付约定**：生图/改图/PPT 三入口，示例可带入草稿；明确目标、原图/材料、输出格式、完成条件 | 现有张榜/任务数据，不另建任务系统 | 用户不懂 abilities 也能发出可执行任务；缺必要材料先澄清，不乱跑 |
| P0 M03 | **成果生成→保存→领取**：选择并打通一条真实 producer 路径；同任务关联、版本/哈希、权限、上传失败可恢复 | `agent_task_artifact`、现有 deliverables/storage/正式交付 | 无开发者搬运，真实图片/可编辑 `.pptx` 在刷新和 Agent 离线后仍可领取；完成状态不得早于成果可用 |
| P0 M04 | **有效进度与失败恢复**：任务当前阶段、最后更新、等待谁、失败原因、下一步；防重复执行、取消语义诚实 | 既有状态/事件/回执/幂等 | 刷新不丢任务；断连能恢复；重试不重复执行；取消未被确认时不伪报已停 |
| P0 M05 | **最小人工验收与修改**：看结果→要求修改/确认完成，修改生成新结果版本，旧版可追溯 | 已有 formal delivery/CAS/decision/rework | 一条真实任务完成“交付→修改→再交付→确认”，不是仅检查空态或按钮 |
| P0 M06 | **回来能继续用**：我的任务入口、待确认结果、成果历史、完成/失败通知（优先站内） | 任务列表、会话、已有消息中心；先核对事件接线 | 关闭页面再回来能找到任务/结果，不必持续盯地图或翻聊天 |
| P0 M07 | **默认私有和明确副作用边界**：仅自己的 Agent/任务、数据隔离；模型/授权来源可解释；使用成本不伪报为零 | 现有 task/Agent ACL、owner 绑定 | 第二身份/client 的受控负例拒绝；不因角色标签/分数授予权限；付费调用需单独授权 |
| P1 M08 | **基本技能与真实就绪说明**：`image.generate`、`image.edit`、`presentation.create` 三项可实测的交付能力；未知诚实展示 | runtime abilities + 简单目录映射 | 让用户知道“能交什么、不能做什么”，而不是先建完整 taxonomy/总结引擎 |
| P1 M09 | **结果复用与体验整理**：保存模板/从旧任务起草，名称采用“发布任务（张榜）/选择助手（点将）”双标识 | 既有详情、草稿/路由 | 第二次同类任务明显少重复输入，普通用户能独立找到动作 |

M01–M07 是目标闭环，不表示每项都从零开发；先盘点每条已实现路径，把状态标为“复用/接线/修复/新增/待授权验证”，再估算工作量。

### 5.1 文件生产和输入素材已成为 MVP 必需，而非只读成果列表

图片生成/编辑和 PPT 不能用“有文字回复”替代。新增/补通的最小能力包括：

- **输入**：改图所需原图上传/选择与私有访问；PPT 所需文字和图片资料接入。输入素材不冒充 Agent 已交付成果。
- **执行**：实际图片生成/编辑工具与实际 `.pptx` 生成器；未知/不支持时明确说明，不能仅凭模型名、角色标签或本编程助手工具判断产品已具备。
- **保存**：真实文件校验、可信 producer 上传、task/run/原版本绑定、持久化、预览和精确下载；优先复用既有 artifact/正式交付，不另建成功台账。
- **修改**：用户主要通过 Agent 对话提出修改，原图、图片修改版、PPT 修改版分别保留；修改请求固定源版本，失败不覆盖原件。界面只做上传、只读预览/下载与版本选择，不建设图片/PPT 在线内容编辑器；可编辑 `.pptx` 指下载后在办公软件中编辑。
- **恢复**：文件已生成而入库失败时恢复保存，不盲目重新调用 Provider；结果未知先查询，不自动造成重复成本。

若确需改 `isp-install`/客户端，单独明确新增范围；本轮不自动撤销此前的范围限制。不能借用户 JWT 伪造 Agent 上传、扫描工作目录，或由开发者手工搬文件后宣称闭环已通。

### 5.2 成本与可用性

“不提供平台交易”不等于“模型执行免费”。受控测试仍须明确使用谁的运行时/Provider、允许什么任务、什么额度或资源边界。MVP 可以在已有授权范围内运行，而不等待真实资金市场；未知费用显示未知，不以参考估算冒充账单。

性能慢先记录耗时和证据，允许用户继续等、取消或回来再看；不以任意 1/3/5 秒门槛取消正常请求。真正的身份失效、用户取消、网络错误、配置传输超时和锁归属仍须处理。

## 6. 原四项新需求怎么放进 MVP

| 原需求 | MVP 保留的最小部分 | 后置部分 | 理由 |
| --- | --- | --- | --- |
| 模型展示/按费用定义智力值 | 有可信来源就显示模型/观察时间，未知不猜 | 计费智力值归一化、完整价格簿治理 | 模型透明有用；费用高低分数不能帮助证明一单能交付 |
| 揭榜模型费用 | 明确执行成本承担者/是否可能收费；有可信估算可附带展示 | 全自动任务 token 估算、Provider 账单/真实结算 | 不让预算功能阻塞不收费的产品闭环，也不能隐瞒底层调用成本 |
| 是否接外单 | 默认仅 owner，服务端边界必须保留并验证 | 外部 opt-in、邀请接受、公开发现 | 先把自己的任务做成，不必先解决双边市场 |
| 可交付技能/自动总结 | 少量实际验证的技能说明、任务模板、交付示例 | 多分类候选引擎、规则重放、自动总结、市场商品 | 没有成功交付数据，自动总结没有可靠素材；先有成果再沉淀 |

原 `juyiting-agent-model-governance` 的安全/费用诚实原则保留，设计文档不删除。**改变的是交付顺序和第一版范围，不是放弃需求。**

## 8. “不是 Demo”的验收定义

### 8.1 产品闭环验收：必须来自真实结果

各目标场景及已声明支持的文件格式分别使用用户真实需求/授权材料，按下面流程留证（需另明确真实执行与必要业务写入/用量授权）：

1. 用户自己从模板发任务，能说清期待收到什么；界面明确目标 Agent 与权限/成本边界。
2. Agent 真实收到任务并开始执行，任务/run 与回执可关联；不能用预录响应或 mock。
3. 需要补材料时用户能补，等待/失败原因可见，不是无限“处理中”。
4. 真实图片或 `.pptx` 自动保存，用户能预览、打开并带走；PPT 正文可编辑，改图结果可与原图对照，不靠开发者复制聊天或从主机取文件。
5. 用户提出一个真实修改意见，系统产生新版本，保留旧版本与裁决，不重复跑整单或覆盖历史。
6. 用户确认结果满足约定；重新登录/刷新、Agent 离线后仍能找回已保存成果。
7. 使用授权的另一身份/client fixture 验证不能读取或改写，不扩大到真实无关用户数据。
8. 演示一次可恢复的失败/断连或重复请求，不吞结果、不重复派单、不虚报完成。

场景数量取决于真实风险覆盖，不设没有推导的成功率/耗时硬门槛。首次成功任务也不能代表全平台成熟；后续试用继续记录失败和用户采用情况。

### 8.2 价值验收：用户有没有真的省事

记录而非臆测：

- **采用：** 输出是否被用户用于实际文档/沟通/工作，不仅点了“验收”。
- **节省：** 同类工作原先的主动整理/编辑时间，与此次投入时间；等待时间另记，不编造节省比例。
- **介入：** 有没有开发者代配置、搬运成果、改状态；受控试用的首次接入协助要单独标注，不能掩盖任务执行仍靠人工救火。
- **重复使用：** 用户是否愿意拿下一份真实材料再来一次；失败原因、修改次数、主动放弃原因是什么。
- **可信度：** 无来源事实是否明确待核对、约定交付项是否齐全、费用是否可解释。

如果输出仍需从头重写，或每次都需要开发者后台收尾，即使所有接口返回 200，也不能宣布价值 MVP 已交付。

## 9. 推荐下一步：先做一条“黄金任务”差距验收，不先堆功能

先盘点并冻结一条准确链路：

`用户模板 → task → 显式自有 Agent → 真实接收/执行 → 成果生产/入库 → 用户取件 → 要求修改 → 新版本 → 验收`

为每一箭头记录实际 API/消息、现有代码、开关、授权、证据、失败表现，分为“已有可复用”“缺接线”“缺实现”“未测试”；不要把整套 R2 或 Runtime 全重写。第一项执行应是**现有 Agent 与 artifact producer 链路盘点**。

随后在明确目标 Agent、原图/演示材料、允许用量、允许写入的测试任务和恢复措施后，分别做生图、改图和 PPT 的真实端到端验收。失败在哪一段，先修哪一段。实际闭环跑通之后，再启动完整计费智力值、外单和技能自动总结。

本次仅交付评估、证据及路线图修订建议；未改 API/Web 代码、运行台账、生产数据或开关，未创建 Reviewer/实施任务，未构建/部署。自有浏览器已关闭，私有登录 profile 已删除。
