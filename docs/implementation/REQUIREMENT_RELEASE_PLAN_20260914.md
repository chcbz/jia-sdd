## 1. 版本规则

- **补丁版本 (`1.0.x`)**：仅线上缺陷、可用性、兼容性或发布/监控问题；可独立发布，不夹带新需求。本版本规划不接管正在另一会话处理的 BUG。
- **小版本 (`1.x.0`)**：一个对用户可说明、可验收的能力包。API 与 Web 可同一发布列车发布，但组件自身版本仍按各仓库的版本策略维护；不强制把 API `1.1.2-SNAPSHOT` 改成与 Web 相同的数字。
- **大版本 (`2.0.0`)**：涉及真实资金扣减/退款、生产数据迁移、外部付费 Provider 或不可逆业务承诺的完整产品能力。不得由“源码已存在”或模拟 ACK 自动升级。
- 每个版本只包含已完成 Owner 自检、已合入 `develop` 的候选；正式测试、构建、同 Run 制品和部署使用既有 Flow。不得创建独立 Reviewer 队列或全局 Writer 队列。
- `default-off` 功能可以随技术版本发布，但不得被计为该能力的**产品交付**；真正启用、身份验收、付费调用与生产 DDL 保持单独验收项。

## 3. 并行与依赖

### 可并行的四条主线

1. **体验线**：`1.1.0` 的案卷阁、横竖屏、公测验收可并行；共享 Web 路径时按文件范围拆分。
2. **运行时线**：`1.2.0` 原生 Agent 兼容可与体验线并行；它依赖当前 API 回归与受控客户端，但不依赖经济功能。
3. **协作线**：`1.3.0` 可先并行推进 E05/E06、E07/E08、F01/F02/F06 的独立路径；E03→E04、E01→E02/E07 等保留真实依赖。
4. **平台线**：`1.5.0` 的 F03 诊断、测试/观测准备可与上述并行；F04/F05 与完整 G 系列按 M4/M5 前置条件推进。

### 必须串行或显式隔离的边界

- `1.3.0` 的同一任务事件/事务路径、同一 API/Web 文件范围不能并行写入。
- `1.4.0` 的真实语音调用、`2.0.0` 的真实资金/退款/租金，必须按用户批准的身份、额度和幂等边界串行执行。
- 生产迁移、生产 DML、真实 Provider 调用、KMS/Broker 启用不是普通版本发布的隐含权限。
- Flow 中的 API 重型验证、隔离 MySQL/Rabbit 等仍按实际资源互斥等待；这不限制无冲突源码开发并行。

## 5. 每个版本的完成定义

一个版本只有同时满足以下条件才标记“发布完成”：

1. 版本范围中的候选已合入组件 `develop`；
2. 对应 Flow 对精确提交的测试、构建、同 Run 制品与部署成功；
3. 线上健康和该版本的最小业务 readback 通过；
4. `specs/INDEX.md`、对应 `delivery-status.md` 增加日期补充，明确已交付边界与未启用边界；
5. 若涉及身份、资金、迁移或 Provider，已有该次受控执行的明确授权和审计回执。

仅有源码 accepted、构建成功、健康检查、默认关闭发布或模拟 ACK 时，版本只能标为“技术发布/待激活”，不能标为产品功能完成。

### 8.3 发布前后的最小清单

**发布前**：固定版本范围和 remote SHA；确认无活动同流水线 Run；Owner 完成相关自检；Flow 产生同 Run 制品。  
**发布中**：不手工重启/停止 foreign 进程；只由 Flow 负责安装和取消；后端遵守 00:00 汇总窗口。  
**发布后**：记录 Flow Run、制品摘要、部署单、API health 或 Web 资源比对；执行版本的最小业务 readback；将未启用/待用户验收明确保留。  
**通知**：完成/异常先写当前会话和站内监控通知；SMTP AUTH526 未恢复前，邮件只作为尽力而为渠道，不能作为唯一完成通知。

## 10. 发布版本与 Commit 的关系（采用）

**发布版本以不可变 Release Manifest / 根仓库集成 commit 为唯一锚点；前后端开发版本只保留为可选元数据，不参与发布版本计算或对齐。**

CYF 是根仓库协调 API、Web 两个独立仓库的结构，因此“只绑定一个 API commit”或“只绑定一个 Web commit”都不足以定义一次发布。一次发布的事实对象是：

1. 一个 release manifest（推荐提交到根仓库）或对应的根仓库 integration commit；
2. 它固定引用的 API commit/tree 和 Web commit/tree；
3. 两侧对应的 Flow Run、同 Run 制品摘要、部署记录与线上核验；
4. 本次启用的 feature flags、迁移和授权边界。

`package.json` 的 `version` 与 Gradle 的 `Implementation-Version` 用于组件开发和诊断；它们**不需要一致，也不决定“当前发布了什么”**。例如当前 Web `1.0.0` 与 API `1.1.2-SNAPSHOT` 可以属于同一个发布 manifest。

### Manifest 最小字段

```json
{
  "releaseId": "2026.09.15.1",
  "rootIntegrationCommit": "<40-char-root-sha>",
  "api": {
    "commit": "<40-char-sha>",
    "tree": "<40-char-tree>",
    "flowRun": 0,
    "artifactSha256": "<sha256>"
  },
  "web": {
    "commit": "<40-char-sha>",
    "tree": "<40-char-tree>",
    "flowRun": 0,
    "artifactSha256": "<sha256>"
  },
  "featureFlags": {},
  "migration": "none",
  "verification": {
    "apiHealth": "UP",
    "webOnlineProof": "<evidence-ref>"
  }
}
```

### 规则

| 场景 | Release Manifest 如何关联 |
| --- | --- |
| 仅 Web 变更 | 生成新 `releaseId`，Web 指向新 commit/Run/制品；API 复用已上线的 commit/制品。 |
| 仅 API 变更 | 生成新 `releaseId`，API 指向新 commit/Run/制品；Web 复用已上线的 commit/制品。 |
| 前后端协同需求 | 同一 manifest 同时固定两端新的 exact commit/Run/制品；根仓库 gitlink 更新形成可复现组合。 |
| default-off 技术发布 | manifest 明示 flag 为关闭、业务验收未完成；不能把技术发布写成需求交付。 |
| 资金/迁移/Provider 启用 | manifest 增加授权、额度、迁移、回滚和审计回执；仍以 exact commit/制品为主体。 |

因此，本路线图中的 `1.1.0`、`1.2.0` 等仅是面向用户和规划的**发布列车标签**。实际发布身份应以 `releaseId + rootIntegrationCommit + API/Web exact commits + artifacts` 为准，而不是以 Web/API 开发版本号为准。
