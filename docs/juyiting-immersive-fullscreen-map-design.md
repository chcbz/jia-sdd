# 聚义厅沉浸式满屏地图与热点交互详细设计

**状态：** 待实施
**日期：** 2026-07-18
**范围：** `web/` 聚义厅前端地图舞台；不涉及后端接口、Agent 数据边界或任务业务规则。

## 1. 背景与原始需求

聚义厅是用户进入系统后的主要沉浸式入口。其主地图为横向梁山场景，承载人物选择、名册、悬赏榜、招贤令、典籍等热点入口。当前移动端竖屏体验存在两个直接问题：

1. 地图以完整展示优先，在竖屏仅占屏幕中部约三分之一，剩余区域为深色留边，视觉上不像沉浸式主舞台。
2. 地图热点在竖屏下存在“看得到但点不动”或点击位置偏移的问题，影响名册、悬赏等核心入口的可用性。

原始业务诉求归纳为：

- 聚义厅地图在手机竖屏也应以地图画面充满可视区域，不保留显著黑边。
- 地图热点与人物在任意屏幕比例、缩放、拖拽、横竖屏切换后，均须可稳定点击。
- 用户仍能通过拖拽、缩放和“回主厅”访问当前视野之外的地图内容。
- 横屏继续提供更宽阔的全景体验，但不再把“沉浸式体验”完全依赖于用户主动切横屏或浏览器全屏权限。

## 2. 业务痛点与业务价值

### 2.1 业务痛点

| 痛点 | 当前表现 | 业务影响 |
| --- | --- | --- |
| 首屏不沉浸 | 竖屏地图按完整比例缩小，大面积留边 | 用户认为页面未加载完整或产品完成度不足 |
| 核心入口不可达 | 可见热点点击无响应或需点击偏移位置 | 名册、悬赏、招贤令等业务转化链路中断 |
| 交互心智冲突 | 画面按 `fit` 展示，输入按“铺满”坐标换算 | 用户无法建立“所见即所得”的点击预期 |
| 横屏能力不显性 | 横屏按钮兼具方向、全屏含义，失败时只提示旋转设备 | 用户不理解如何获得更好的地图体验 |
| 布局变化后失配 | 侧菜单、浏览器地址栏、软键盘等导致可视容器变化 | 地图、相机和点击区域可能不同步 |

### 2.2 业务价值

- **提升首屏感知质量：** 地图始终是视觉主体，强化“聚义厅”的场景化产品定位。
- **恢复业务入口可用性：** 热点点击可直接打开面板，降低任务指派、Agent 管理、招贤令等流程损耗。
- **统一多端体验：** 手机竖屏、手机横屏、平板和桌面均采用同一套坐标模型，减少设备特定问题。
- **降低后续扩展成本：** 新增热点、动态人物、地图层或相机行为时，不再为每种缩放模式单独修补命中逻辑。

## 3. 现状架构与问题根因

### 3.1 当前职责划分

| 模块 | 当前职责 |
| --- | --- |
| `JuyiHall.vue` | 页面数据加载、业务面板、选中上下文、进入时隐藏全局 App Bar |
| `HallStage.vue` | 地图宿主容器、加载态、横竖屏控制、窗口视口监听、挂载 melonJS |
| `JuyitingGame.js` | 初始化 melonJS canvas、加载地图资源、将业务数据同步给场景 |
| `HallScene.js` | 相机、地图渲染、人物与热点命中、指针事件转换 |
| `sceneInputController.js` | 区分点击、拖拽、缩放手势，并调用热点或人物命中回调 |

页面容器已经具备占满应用可用区域的基础：聚义厅隐藏全局 App Bar，`app-content` 和地图舞台采用 flex 布局填充。因此，“地图只占三分之一”并非页面外层高度不足，而是画布内部的地图显示策略与竖屏比例不匹配。

### 3.2 当前缩放与输入链路

当前地图设计尺寸为 `1664 × 928`，为横向约 16:9 场景。melonJS 初始化时使用：

```js
scale: 'auto',
scaleMethod: 'fit'
```

`fit` 的语义是完整保留设计比例。当宿主容器是手机竖屏时，它会把 16:9 地图缩小至容器宽度可容纳的尺寸，剩余高度形成 letterbox 留边。该策略能展示整张地图，但无法达成“满屏沉浸”。

与此同时，现有 `_clientToViewport()` 将浏览器指针坐标转换成游戏视口坐标时，使用：

```js
scale = Math.max(displayWidth / viewportWidth, displayHeight / viewportHeight)
```

该计算是 **cover（铺满并裁切）** 的比例模型，而不是 `fit` 的比例模型。并且换算基准取 `.melon-layer` 的完整矩形，而不是地图实际渲染内容区域。最终造成：

```text
用户看到：fit（完整地图 + 上下留边）
代码换算：cover（地图已铺满整个容器）
命中判断：以错误坐标反算世界坐标
结果：热点/人物的点击区域相对画面偏移
```

竖屏比例与 16:9 的差距越大，偏移越明显；这解释了“热点区域现在就点不动”的现象。

### 3.3 根因结论

1. **体验根因：** `fit` 与“竖屏无黑边、地图为主画面”的产品目标冲突。
2. **功能根因：** 渲染变换与输入反变换使用了不同的缩放模型，未共享同一组 `scale` 和 `offset`。
3. **稳定性根因：** 容器尺寸变化只依赖 `window` / `visualViewport` 事件，未以地图宿主的实际尺寸作为唯一真源；相机更新也未覆盖渲染画布与命中变换的全链路同步。

## 4. 目标、非目标与设计原则

### 4.1 目标

- 移动端竖屏地图视觉上无显著黑边，画布画面覆盖整个地图舞台。
- 任何可见热点和人物，其视觉位置与实际命中位置误差不超过 12 CSS 像素。
- 热点命中适配矩形和多边形区域，兼容相机缩放、拖拽、旋转、浏览器地址栏伸缩与桌面侧栏变化。
- 保留地图完整访问能力：被裁切的边缘内容可通过拖拽、缩放和“回主厅”访问。
- 保持现有 Vue 业务面板、API、`/agent/map` 与 `/agent/roster` 的数据隔离规则不变。

### 4.2 非目标

- 不将地图改为非等比拉伸；`stretch` 会使人物、建筑和热点视觉变形。
- 不改造为 Three.js 或替换 melonJS。
- 不改动地图热点对应的业务面板、后端接口或权限模型。
- 不承诺自动进入浏览器原生全屏。原生全屏通常需要用户手势，且部分移动端浏览器不支持方向锁定。

### 4.3 设计原则

1. **所见即所得：** 渲染、相机和点击必须使用完全相同的空间变换。
2. **画面优先：** 移动端默认采用满屏沉浸视图；完整地图通过相机导航而非留边保证。
3. **单一尺寸真源：** 以 `.melon-layer` 的 `getBoundingClientRect()` / `ResizeObserver` 结果为准，不以窗口尺寸替代容器尺寸。
4. **渐进兼容：** 不支持原生全屏或方向锁定时，地图仍在普通页面内提供满屏覆盖和正常点击。

## 5. 技术方案

### 5.1 总体方案：统一为 cover 型满屏舞台

默认地图舞台改用等比 **cover** 语义：地图按较大比例缩放至覆盖舞台宽高；超出视口的地图区域自然裁切，由相机拖拽和缩放访问。

melonJS 采用与 cover 对应、且保持设计比例的缩放模式（实施时以当前安装版本支持的 `fill-min` / `fill-max` 行为和实际验证结果为准），不采用 `stretch`。核心不是某一个字符串，而是保证渲染结果满足：

```text
renderScale = max(containerWidth / designWidth, containerHeight / designHeight)
renderOffsetX = (containerWidth - designWidth * renderScale) / 2
renderOffsetY = (containerHeight - designHeight * renderScale) / 2
```

在竖屏中，`renderScale` 将由容器高度主导：地图高度填满屏幕，左右超出的部分由裁切隐藏；在横屏中，地图接近完整显示。两种状态都不产生显著黑边。

### 5.2 统一坐标变换模型

新增一个纯函数模块，例如 `web/src/game/viewportTransform.js`，作为唯一的显示空间与输入空间转换真源。

建议公开接口：

```ts
type ViewportSize = { width: number; height: number }
type DisplayRect = { left: number; top: number; width: number; height: number }
type ViewportTransform = {
  scale: number
  offsetX: number
  offsetY: number
  mode: 'cover'
}

createViewportTransform(display: DisplayRect, viewport: ViewportSize): ViewportTransform
clientToViewport(clientX: number, clientY: number, display: DisplayRect, transform: ViewportTransform): { x: number; y: number }
viewportToClient(x: number, y: number, display: DisplayRect, transform: ViewportTransform): { x: number; y: number }
```

转换规则：

```text
viewportX = (clientX - rect.left - offsetX) / scale
viewportY = (clientY - rect.top - offsetY) / scale

clientX = rect.left + offsetX + viewportX * scale
clientY = rect.top + offsetY + viewportY * scale
```

要求：

- `HallScene` 的输入包装器只能调用该模块，不再自行计算 `Math.max`、`offsetX` 或 `offsetY`。
- 用同一模块提供的正向换算，将热点世界/视口边界投影为调试覆盖层，供测试验证“画面位置”和“命中位置”一致。
- 若 melonJS 返回了实际 canvas 内容矩形或缩放数据，优先使用引擎真实值；若没有，则使用宿主尺寸和设计视口推导，且两者只能存在一个有效真源。

### 5.3 容器尺寸与相机同步

`HallStage.vue` 在 `melonContainerRef` 上注册 `ResizeObserver`，而不只监听窗口：

1. 首次挂载后读取 `.melon-layer` 的实际 `contentRect`。
2. 发生尺寸变化时在 `requestAnimationFrame` 中合并多次事件。
3. 将容器宽高传入游戏外观层和 `HallScene.resizeViewport()`。
4. 同步执行：画布显示尺寸更新、相机视口更新、变换缓存失效、回主厅按钮状态刷新。
5. 软键盘场景仍沿用现有分类逻辑：键盘仅影响输入与面板高度时，不重置地图相机。

`window.resize`、`visualViewport.resize`、方向改变事件继续保留，作为触发容器重新测量的信号；实际更新数据必须来自 `ResizeObserver` 或元素 `getBoundingClientRect()`。

### 5.4 相机与可达性策略

满屏 cover 会裁切地图边缘，因此需要明确相机策略：

- 首次进入：根据容器比例选择 `mobilePortrait`、`mobileLandscape`、`tabletLandscape`、`desktop` 预设，竖屏初始位置聚焦大厅核心区。
- 竖屏：允许单指拖拽浏览，双指缩放；默认缩放不应把可交互热点缩小至难以点击的尺寸。
- 横屏：优先显示更大范围；用户点击“横屏”后可尝试原生全屏与方向锁定，失败时不阻断普通满屏地图。
- 回主厅：重置到当前设备预设，而不是强制恢复为完整地图 `fit` 视图。
- 热点保障：对当前视野内的热点使用最小命中区域和触摸容差；屏外热点不应被误触发。

### 5.5 热点、人物与面板事件链

```text
浏览器 pointer 事件
  → clientToViewport（统一变换）
  → camera.screenToWorld
  → 热点多边形/矩形、人物边界命中
  → HallScene.onHotspotClick / onAgentClick
  → HallStage emit('open-panel') / emit('select-agent')
  → JuyiHall 打开对应 Vue 面板或更新选中 Agent
```

热点命中规则保持现有语义：

- 多边形热点用世界坐标点在多边形内判断。
- 普通热点用世界坐标矩形判断。
- 人物与热点重叠时，保持当前优先级；若产品认为人物优先，应显式在输入控制器中定义，而不依赖数组顺序。
- 触摸设备使用独立 `touchSlop`，仅在世界坐标中应用一次，避免被 CSS 缩放重复放大。

## 6. 实施细节与代码拆分

### 6.1 第一阶段：建立可验证的变换基础

1. 新增纯函数变换模块及单元测试，覆盖 16:9、竖屏长屏、平板和带 CSS 偏移的容器。
2. 将 `HallScene._clientToViewport()` 改为调用统一模块。
3. 增加开发环境调试开关：显示当前 `scale`、`offset`、视口、最近一次点击的 client/viewport/world 三组坐标和热点边界。
4. 不改变业务热点数据、地图资源或相机预设，先证明当前 `fit` 下也能获得正确命中。

**阶段验收：** 在当前 `fit` 模式下，逐个点击五个热点及地图人物，点击坐标与可视标记一致；此阶段只修复功能偏移，不改变产品视觉策略。

### 6.2 第二阶段：切换为满屏 cover 舞台

1. 在 `JuyitingGame` 的画布配置中切换至经验证的等比填满模式。
2. 明确 `.melon-layer` 与 canvas 的宽高、裁切和背景规则；舞台背景与 canvas 内容同色，但不可再以留边方式暴露空白。
3. 更新相机的移动端竖屏预设，使大厅核心、至少一个人物和一个热点在首次进入时处于可见区域。
4. 保留地图边缘区域的访问方式：拖拽、缩放与回主厅；不以缩小地图换取“全内容同时可见”。
5. 把方向按钮文案改为明确的“横屏全景”或同等含义，并在原生全屏受限时提供简短引导，不把功能成功依赖于权限。

**阶段验收：** 典型 390×844、430×932、768×1024、844×390、1366×768 视口下，地图舞台无显著黑边；所有可见热点均可点开正确面板。

### 6.3 第三阶段：容器重排与回归保护

1. 接入 `ResizeObserver`，处理桌面侧菜单开合、浮层关闭、地址栏变化、横竖屏切换。
2. 将容器尺寸变化统一节流到动画帧，防止 resize 风暴重置相机。
3. 在 `HallStage` 卸载时断开 observer、取消 animation frame，并清理场景输入监听，避免重复挂载。
4. 维持现有加载失败降级逻辑；melonJS 初始化失败时，应保留明确错误提示和可恢复入口。

**阶段验收：** 连续切换横竖屏、开关侧菜单、拖拽和缩放后，不出现画布缩小、热点偏移、重复回调或内存泄漏。

## 8. 风险、约束与应对

| 风险 | 说明 | 应对 |
| --- | --- | --- |
| 满屏裁切隐藏边缘热点 | cover 不可能同时完整展示横图和填满竖屏 | 通过拖拽、缩放和竖屏相机预设保证可达；首次视野优先放核心入口 |
| 引擎缩放模式语义差异 | melonJS 的 `fill-min` / `fill-max` 需要以当前版本实际渲染确认 | 在第一阶段建立可视调试和截图验证；以实际 canvas transform 为最终真源 |
| 双重缩放 | 引擎内部 scale、CSS 尺寸、相机 zoom 若重复参与计算会再次偏移 | 明确“显示变换”和“相机世界变换”职责；输入仅按同一显示变换反算一次 |
| 软键盘误触发相机重置 | 移动端 visual viewport 改变频繁 | 保留键盘分类逻辑，键盘事件只更新可视高度，不自动 reset camera |
| ResizeObserver 事件风暴 | 地址栏动画、侧栏 transition 会连续触发 | 使用 animation frame 合并，尺寸无实质变化时不更新 |
| 原生全屏兼容性 | iOS/Safari 与嵌入式浏览器可能拒绝 API | 原生全屏视为增强功能；普通页面中的 cover 舞台必须独立可用 |
| 回归业务面板 | 输入层改动可能影响热点 emit | 为每个热点增加事件断言，保持 `open-panel` 契约不变 |

2. 在测试环境完成竖屏与横屏人工验收矩阵。
3. 部署前端静态资源，保留当前版本备份。
4. 发布后使用前端埋点或调试日志观察：热点点击次数、热点点击后面板打开成功率、输入坐标异常、场景初始化失败率。
5. 若发现单个热点偏移，优先修复其地图世界坐标或命中多边形；不得回退为 `fit` 留边来掩盖输入问题。

## 10. 实施决策摘要

- 默认视觉策略：**等比 cover 型满屏地图**，而非 `fit` 留边或 `stretch` 变形。
- 交互策略：**一套共享的显示变换**驱动绘制参考、指针换算和命中调试。
- 自适应策略：**容器尺寸优先**，通过 `ResizeObserver` 更新，而非仅监听 window。
- 可达性策略：**相机导航访问裁切区域**，而不是为了全图可见牺牲首屏沉浸。
- 兼容策略：**原生全屏为可选增强**，不作为地图满屏或热点可用的前置条件。
