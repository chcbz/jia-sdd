## 2. 测试层次与复用

- 单元：导航reducer、scope键、草稿CAS、status→action映射、私有/正式adapter、方向ownership。
- 组件：真实挂载JuyiHall/HallWorkWindow/Picker，必须包含父子事件及v-if/v-show生命周期，避免再出现“接口200但详情没打开”。
- 集成：实际API客户端到Controller/Service，scope隔离、事务回滚/唯一约束、旧DTO兼容、游标/部分失败；仅mock api.put不足以证明真实链路。
- 浏览器：Demo的87项改造为真实应用脚本，不能照搬其localStorage/手动成功按钮；下载核对类型、文件头和hash，打开真实Office/PDF。
- Runtime：现有持久收件箱与file-bridge测试扩展；同一Provider运行的副作用计数明确。
- 真机：优先用户实际渠道，记录机型、OS、浏览器/微信及宿主版本，分别记录物理旋转、按钮、键盘、返回、原生下载。不以UA仿真顶替。
- 既有测试选择器参考release树：`tests/juyiting-experience-mode.test.js`、`juyiting-mini-program-orientation.test.js`、`juyiting-babao-hall-style.test.js`、`personal-workspace-execution*.test.js`、`personal-workspace*-links.test.js`、`juyiting-task-workspace-*.test.js`。API复用PersonalWorkspace*、FormalDelivery*、安全/mapper相关测试，按最终改动补足。
- 证据复用键仍为Git tree+selector+DB fixture digest；未改树不重复全套。正式Gradle只经orchestrator；本轮文档不运行这些测试。

## 3. 业务价值验证，不只验UI

### 3.1 探索性可用性测试

建议先邀5名未参与设计、确有文档处理需求的目标用户（便于小轮发现问题的资源建议，不是统计功效/发布阈值），使用同难度但不同内容的任务，旧/新界面交替顺序以减少学习偏差。只用非敏感样本；真实收费执行另授权。

脚本：找入口→形成草稿→选一版材料→交办→关闭回访→解释状态→领取成果→提出修改。研究人员不指路；记录主动求助、误点、重输、误把核对当重新执行及退出理由。若旧链路无法完成，记录阻断，不逼用户重复已知危险操作。

### 3.2 试点指标口径

| 指标 | 分子/分母或计时 | 使用方式 |
|---|---|---|
| 无协助任务完成 | 无研究人员介入且完成全部指定步骤人数/尝试人数 | 旧新同脚本比较，失败/放弃不剔除 |
| 可用成果率 | 取得可打开且用户确认满足目标的成果事项/明确交办事项 | 排队、未知和失败单列，不能只统计终态成功者 |
| 恢复成功 | 回访后找到同一草稿/运行/成果且上下文正确次数/回访尝试 | 记录身份、入口和浏览器边界 |
| 重复输入/误重试 | 每条任务的重写与意外新执行次数 | 必须结合录像/网络，不只看点击数 |
| 首个可用成果耗时 | 从明确交办到首次可用成果，未完成记未完成 | 区分UI操作/队列/Provider/回传，不以超时剔样本 |
| 修改成功 | 可找回旧版且新成果满足修改要求事项/提出修改事项 | 不把重新生成无关联新文件算通过 |
| 服务成本 | 实际已知Provider成本、人工支持时长；未知单列 | 不使用猜测价格或“每次便宜30%”宣传 |
| 再次使用 | 约定观察期内再次完成真实事项用户/有完整观察期试点用户 | 观察期实施前按业务周期约定，不用小样本承诺留存 |

可选最小事件：draft_started/draft_saved/materials_confirmed/submission_acknowledged/reconciliation_requested/result_opened/download_failed/revision_submitted/return_resumed/help_requested。浏览器触发下载仅记录download_started；实际可打开/可用由独立验收记录，不把点击当下载完成。事件仅使用匿名化actor、ref、来源、模式、错误码/耗时，不带正文/文件名。

初始无业务基线，不定“提高30%”硬指标。M0冻结采样/同意/观察周期，P01形成对比结论：是否值得扩大试点、仍阻断哪种任务。不能仅凭用户认可Demo就宣布可推广。

## 4. 验收分界

- M1交互骨架：可在开发预览评估连续性，不称真实交付可用。
- M2受控试点候选：A01–A15、A18–A22相关路径有exact证据，至少一个真实授权业务闭环通过；未开放格式/宿主明确列限制。
- M3完整体验：A16/A17及整套既有入口回归，完成P01用户试点与事实总结；该结论仍不代表新商业结算/新模型能力完成。
- 问题按实际证据定位、Owner自检；不创建独立Reviewer、任意耗时或资源固定门槛。
