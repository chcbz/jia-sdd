### 实际执行顺序与收口

0. **先走新用户外单主线**：无自有Agent新用户→找开放吴用→确认自动首轮→连续议事→资料/真实成果→验收→重新进入；第二新用户顺序正常使用及手机路径一并验证。不能以吴用所有者账号成功代替。
1. **一件文字事项走到底**：N01/N02→N03/N04→N09→N16→N20→N22/N23，中间顺带检查话头和事项切换。
2. **一件图片事项走到底**：吴用看图→生成/修改→多稿预览→验收；林冲按实际支持能力独立跑一条正常流程，不机械复制不支持的能力。
3. **一件资料事项走到底**：选材/上传/取消/范围→PDF讨论与摘要→预览→验收，避免为每条断言重复模型调用。
4. **补实际交互**：正常停止回复、语音输入、手机流程。共用私议/公议只做正常连续对话补测，不开展故障或多Agent竞争专项。
5. 每条记录实页结果、耗时和证据；关注操作反馈、连续对话能否继续、文件是否真正可用以及是否多绕步骤。不设置无依据的请求截止时间。
6. 全部正常场景按PASS/FAIL/BLOCKED/NOT_RUN如实汇总；缺能力、设备、授权或费用条件不冒充通过。异常专项统一记“本轮不执行”，不因未跑异常场景否定已通过的正常流程，也不宣称全量测试通过。

## 2. 执行约定与测试数据

### 优先级与验证方式

- **P0**：主线可完成、历史投诉、身份隔离、避免重复执行/错误验收。今晚优先。
- **P1**：恢复、复杂资料、多端和并发边界。属于完整清单，不因未执行就默认通过。
- 表中无特殊标记的用例走**真实已登录浏览器**。浏览器页面必须连接受测应用/API/Runtime，不能拿localhost离线原型当业务通过。
- **[隔离]**：故障注入、竞争、权限攻击、损坏数据，只在隔离环境/测试身份执行；不重启或断开共享生产Runtime，不篡改真实历史状态。
- **[补充自动化]**：真实组件/API/Runtime定向测试，不能替代同名主线页面实操。必要应用测试/构建在本地固定候选执行；本地构建发布同批默认上限600秒，保留现有阶段拒绝及本批构建RuntimeMaxSec终止行为；预计或实际超限须向用户申请例外，未获批不延长、不绕过。此限制不用于业务请求或生产服务强杀，不删必要保护。
- 显示顺畅与业务正确分开记录：不能只看Toast、HTTP202、SSE EOF或模型结束，需核对对应业务终态及实际成果。后端只读查询辅助取证，不代替页面触发。

### 共用前置条件

1. 使用专用测试事项，不删除/修改用户历史事项。准备用户A及无权访问A事项的用户B；多Agent测试使用明确可用且属于授权范围的目标。
2. 吴用、林冲各准备一个可用测试事项；记录各自真实技能版本、就绪状态及服务能力。不能凭吴用成功推断林冲，也不能把缺少能力的任务安排给不支持的Agent后当执行缺陷。
3. 资料集：内容已知的短文本与长文本、PNG/JPEG/GIF/AVIF、至少2页PDF、音频、非在线预览格式，以及两个同名不同版本文件。预先记录固定ID/版本/摘要。声明支持的格式执行正例，明确不支持的格式执行解释/保留输入的反例；缺样本记BLOCKED。

5. 桌面与390px、320px视口；移动真机/软键盘另记设备结果，视口模拟不能算真机通过。
6. 模型及技能执行使用明确的测试账号、额度和费用授权；安装即授权不等于授权任意付费执行。不具备条件的实际付费用例标BLOCKED，不偷偷替成mock PASS。

| E06 流式停止后续聊 | 发送→真实回复中停止→确认停止终态→发送下一轮→刷新 | 不撤销原成果、不重发原问题，下一轮可用，停止状态不串轮 |
| E07 断线与重入 | 发起请求→客户端断网/刷新→重新进入同事项→核对原请求→继续议事 | 不新建请求/重复扣费，正文/成果恢复；真实失败可解释 |
| E08 资料与弹层 | 话头记录→更多→点击输入→资料选择→多选/预览/取消→重开/完成→发送 | 一页内完成，外点/Esc合理关闭，不丢草稿、不自动发送，范围准确 |
| E09 新旧话头与事项切换 | 在事项A建立两个话头并续聊→切B→回A→重开旧话头 | 当前事项、Agent、历史、草稿、附件准确隔离 |
| E10 移动完整主线 | 手机上重复E01并穿插语音、资料预览、软键盘开合 | 输入/发送/停止/验收可触达，无横向溢出，不被键盘遮挡 |

## 5. “跑流畅”的记录方式

不先拍一个秒数当后台拒绝门槛，不因慢就取消真实执行。每个E01–E10剧本分别记录：

| 观测项 | 起止点 | 需要区分 |
|---|---|---|
| 点击反馈 | 用户点击→页面出现本次动作的忙态/反馈 | 不拿旧Toast当本次反馈 |
| 请求受理 | 点击发送→本轮权威请求建立 | 准备上下文、上传与服务受理分开 |
| 首个有效答复 | 点击发送→第一段有意义正文 | “处理中”不是模型答复 |
| 本轮完成 | 点击发送→业务终态及最终正文可读 | 流断开不是完成；记录失败/未知 |
| 成果就绪 | 执行提交→真实成果可预览且具备合法验收资格 | 生成、登记、预览分别计时 |
| 可继续操作 | 业务终态→输入/下一轮恢复 | 不应必须刷新、切页或重登录才能继续 |
| UI恢复 | 刷新/重进→原请求和正文/成果恢复 | 不重复POST，不把回放当新执行 |

- 每种关键主线记录首轮与同会话连续轮，标明冷/热状态、网络、资料大小和技能，不拿不同任务耗时硬比。
- 正常等待必须有恰当反馈；错误要能看懂、保留输入、提供真实恢复。卡死、无反馈、无理由重复点击、正常状态黄色警告、重复大块响应均记录体验缺陷。
- 明显长等保留时间线、关联ID与浏览器网络证据；接口、模型、Runtime、成果登记、前端刷新分别归因，不一概“模型慢”。今晚记录不等于重启已暂停的技能启停性能专项。
- 不宣称一次通过代表稳定低延迟；本轮没有既定数值性能验收阈值，完成报告逐项给出实测与剩余体验问题。

## 2026-10-27 正常流程实测补充：修改子请求状态反馈

依据N16正常“生成文件/修改成果”实测BUG05：Runtime已持久记录恢复待核对，原议事仍显示“正在处理”。本补充不增加异常注入用例或重试入口。

- Runtime的`chat.dispatch.ack(status=recovery_required)`必须按原tenant/client、执行者授权、agent、dispatch/message和turn绑定落到原请求；不得只确认传输收件而丢弃恢复事实。
- 已有明确模型输出合同拒绝仍为FAILED；传输超时、引擎受理未知等非明确终态只记RECOVERY_REQUIRED，不推断成功/失败，不自动重放。已经确认的final/cancel/failure不因迟到ACK倒退；重复ACK不产生新执行、事件版本或新请求。
- 请求只有未终结轮次且存在待恢复轮次时，聚合返回已有RECOVERY_REQUIRED状态；终态混合仍沿用PARTIAL。迟到的真实完成事实仍可推进完成。既有reviewProgress.childState/childStateVersion传递真实状态，原只读刷新继续，不新增定时器或POST。
- 修改卡明确提示“执行状态待核对，上一版仍保留；请勿重复提交修改要求”，不能写作“正在原议事继续处理”或已经失败/完成。
- reason只存错误码，不落任意Provider正文/上下文；非错误码输入降为通用恢复码，不拒绝ACK或丢恢复事实。身份/绑定失败仅拒绝该ACK且不得修改别的请求。风险分别为跨用户状态篡改、终态覆盖/重复执行、敏感上下文泄漏；不新增版本/技能开关。

### 2026-10-27 N08 最小跨端修复合同（实现候选，尚未上线）

统一规范仍为 `api/docs/interface-standard.md` v1.4。另起话头不是新事项、重新点将或重新执行；只创建一个归属原事项的空会话。保留现行首轮绑定作为默认入口，新增话头必须有服务端持久、可核验的事项归属，不能直接取消现有binding校验。
