## Completion ordering that the queue must preserve

At this client baseline, `runCodex.finish` sends legacy `task.report`/`codex.result` with `completed` immediately after releasing the workspace lease (`agent-client.mjs:3630`). The API's `AgentLegacyTaskCompatibilityService.updateMemberForReport` maps completion to member DONE; `AgentTaskCollaborationAccessServiceImpl` gives DONE/FAILED only READ_ONLY access. Consequently, sending this terminal report before queued upload/verification/publication finishes can revoke that queue's mutation authorization even while its output run remains ACTIVE. OD02's repaired final authorization deliberately rejects this case; do not weaken it to accommodate client ordering.

For output-bearing commands, persist the model result and pending terminal-notification intent with the immutable output snapshot. Release the workspace lock before network I/O, but emit the terminal business report only after the intended publications finish, or after a deliberate final failure policy. Temporary HTTP outage must retain a recoverable pending transfer without changing the member to DONE/FAILED or rerunning the model. Account for the command inbox/ledger as well: `AgentProtocolController.drain` (`agent-client.mjs:2676–2712`) currently coerces every outcome except `failed` and its explicit `recovery_required` branch into completed. Returning a new `delivery_pending` value without changing this state transition would still produce a premature terminal ACK.

OD04 must test the actual finish → command outcome/ledger → report ordering with a blocked HTTP transfer, then process restart and queue resume, asserting the model invocation count remains one and the terminal report is emitted only at the intended durable boundary. Apply equivalent checks to task-bound chat where its final message can affect task state. Plain text conversations without a manifest preserve their existing completion path. This is read-only handoff analysis, not an implemented queue protocol.
