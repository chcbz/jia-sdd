## 1. 原型里有的，本期就做

| 原型功能 | 产品应达到的效果 |
| --- | --- |
| 一个入口、一张列表 | 自己的Agent详情里进入“管理技能”；已安装和可安装放一起，行内展开，不新增商城页或安装总入口。 |
| 安装 | 在原行选择安装即批准候选声明权限，再获取报价、确认安装；显示进度与结果，成功后更新列表和Agent详情。保持原型流程，不另改成自动报价。 |
| 升级 | 原行显示当前版→目标版、能力变化、权限、依赖与费用；确认后准备、切换、核验。准备失败保旧版，旧任务仍用原版本，不自动重发旧消息。 |
| 详情、启用/停用 | 详情查看输入、权限和运行状态；启停需确认，只影响新调用，保留已授权任务、成果与历史。 |
| 失败重试与未知核对 | 可恢复的准备失败沿原操作重试，不重复购买；结果未知只核对原操作，不自动认定成功/失败。 |
| 离线安装等待 | 合法已绑定的Agent离线时可提交安装，显示等待连接；重连后续原操作，不要求用户再买一次。 |
| 操作记录 | 沿用列表底部的折叠记录，显示真实动作、结果和时间；不扩成独立工作台。 |
| 收起、关闭和手机操作 | 同一窗口内原位展开/收起；Esc先收起再关闭，关闭不取消后台操作；手机保持同一列表。 |

**2026-10-26新增范围：受控卸载。** 原行详情内确认，保留任务/成果/权益，真实回执与目录确认后移出已安装，支持重新安装。具体见合同末节。仍不做指定版本回退、批量操作、平台发布维护页。

“演示设置”“模拟恢复连接”“重置示例”只用于原型，不进入产品。商品、价格、版本和回执改用真实数据，不能把示例0积分或1.1.0当作已经发布的事实。离线安装是原型已有范围，不据此自行扩展其他离线操作。

## 2. 前端、后端、Runtime各补什么

| 部分 | 最小落地方式 |
| --- | --- |
| 前端 | 按原型实现同一列表、行内安装/升级/详情/启停/进度及折叠记录；复用已有市场的权限、报价、购买和原请求恢复逻辑，接真实数据。 |
| 后端 | 复用现有商品、订单、权益、安装记录和消息投递；补升级、启停、离线接纳、可恢复失败重试及记录查询的必要能力。支持原型，不另造通用管理平台。 |
| Runtime | 复用安装器、回执和能力刷新；补受控升级、启停同步、重连恢复，并让旧任务继续使用原版本。 |

### 实现时必须处理的几个缺口

- **升级不是重复购买。** 当前API的首次购买防重、Runtime的同技能安装冲突都需要明确的升级分支，不能删检查绕过去。固定原版本和批准目标；已有权益覆盖就不重复收费，需要费用则明确确认。
- **升级不打断旧任务。** 按原型保留旧任务的精确版本和所需包，新请求在新版核验后使用新版。不能为省实现改成“有任务就不许升级”；所需版本引用与恢复在既有执行/安装记录内补齐，不扩大成通用版本平台。
- **离线等待是真正的后端能力。** 当前购买依赖在线就绪证明，必须补“合法归属及持久Runtime绑定可接纳、重连后再核验投递”，不能只打开按钮或取消身份检查。
- **失败重试不能再次扣费。** 可恢复准备失败保留原操作与资金关系；已经退款或权益终结的历史订单不能伪装成原操作重试。未知先查原回执，不新建替代安装。
- **启停不是本地开关。** 停用后后端拒绝新调用，Runtime同步状态；启用需真实安装/权限/运行核验。已有任务不因普通停用而被取消。

上述是支撑原型必须补的能力，不代表已实现。优先扩展现有记录、接口与消息；确实需要新增字段或入口时只加本功能所需内容，不提前建设整套操作框架。继续遵守 `api/docs/interface-standard.md` v1.2（2026-10-14），保留权限、幂等、事务、包完整性和真实回执。

## 3. 四小时实施计划

**目标：从实际开工T0起，240分钟内完成现有原型对应功能的开发、三端联调和集成验收。** 这是目标排期，不是已经测得的工期保证；本轮已先收口多端合同，但应用实现尚未开工计时；规范工作耗时单列，不计为已完成的产品开发。

验收指在获准的隔离测试环境使用真实产品前端、API、数据库和Runtime完成业务链路，不用原型动画或mock接口代替。生产部署/迁移、真实扣费和付费Provider调用不因本计划自动获得授权；集成验收与生产上线验收分别记录。

### 分工：三端并行，不重画原型

| 负责方 | 交付范围 |
| --- | --- |
| 主Owner（本聊天） | 固定源码和原型，收口三端字段与动作约定、协调联调/本地验证、汇总验收；不另设Reviewer。 |
| Web实现Owner | 原型对应的单列表及全部行内操作、真实数据、异常恢复、记录和手机/键盘交互。 |
| API实现Owner | 升级、启停、离线安装接纳、原操作重试/核对、记录查询；复用交易/安装链，补对应回归。 |
| Runtime实现Owner | 安全升级及旧任务版本保留、启停同步、重连续办、回执/恢复；补故障验证。 |

计划按3个源码Writer并行安排，分别负责Web/API/Runtime且路径不重叠；不是3个依次等待的阶段。需要时使用1个只读test_runner辅助验收，不新增架构/评审轮次。本轮未派发Agent或创建运行任务。实际启动时沿现有台账登记真实任务ID，交接根AGENTS、接口v1.2、工具入口及固定源码；外部Runtime仓库也显式传达CYF规则。

### 240分钟安排

> 以下四小时排程与其Flow资源条件是原任务历史计划，不是当前执行前置条件；现行实施按下节本地验证和实际候选安排，不重启历史排程。

| 开工后 | 工作 | 到点应拿到什么 |
| --- | --- | --- |
| 00:00–00:15（15分钟） | 主Owner核对三仓候选/脏改动、测试环境、既有Flow可用性与近期耗时；确认测试Agent、身份及两个获准技能版本。三端按已定SM-C1核对生产者/消费者及候选差异，不再现场另定字段。 | 绑定SM-C1及同源fixture摘要、各自修改路径；测试环境及数据可用。发现差异回合同修正，不各自变更协议。 |
| 00:15–01:45（90分钟） | 三端并行实现并写定向回归。Web照原型接安装/升级/启停/记录；API补业务缺口；Runtime补替换、旧任务引用和恢复。可工作的接口随完成随接，不等整端结束。 | 所有原型动作有实际实现；最早先取得首次安装的跨端反馈。仅mock自测不能算联调通过。 |
| 01:45–02:30（45分钟） | 真实三端联调：安装→升级→启停，再跑离线等待、失败重试及未知核对；同步修阻断问题。重点验证升级期间旧任务继续原版。 | 主流程与异常链路能贯通；形成精确受测候选及必要测试入口。 |
| 02:30–03:30（60分钟） | 固定候选，启动现有Web/API Flow的受影响测试与构建；并行执行Runtime定向回归、数据库/回执核对和候选对应的浏览器验收。使用隔离环境，不在生产做故障注入。 | 真实Run结果、必要回归结果和制品摘要；失败定位到具体用例，不以提交成功替代测试通过。 |
| 03:30–04:00（30分钟） | 核对最终候选与验收输入一致，完成桌面/手机检查和剩余复测，输出下表逐项结论、证据及预览入口。 | 全项通过才报“验收通过”；否则列明失败/未测项及剩余工作，不把截止时间当成功条件。 |

上表是墙钟时间，三端并行，不是每端各4小时。测试与联调随代码就绪提前穿插；最后30分钟不是大型返工预算。修复若改变受测源码，必须补跑受影响测试/构建，不能拿修复前Run宣称最终候选通过。

### 执行中如何避免拖到最后

- **15分钟检查准备条件**：测试环境、双版本包/升级权益政策、身份和Flow资源必须可核验；缺项立即说明对四小时目标的影响，不用演示商品填空。Flow耗时按实际观察安排，不承诺排队和构建一定在预算内结束。
- **90分钟检查最早闭环**：至少应有首次安装的真实跨端反馈；升级/旧任务留版或离线恢复出现合同阻塞时立即由三端Owner一起定位，不继续各写各的。
- **150分钟检查验收候选**：若仍有主链未通，及时报告超时风险和剩余动作；优先处理阻断，不扩框架、不删原型功能、不靠改成“有任务不能升级”省实现。
- 四小时是交付目标，不是业务等待超时，不据此强停用户任务或他人Flow。未通过项如实保留，不能为了按时签收跳过权限、资金、幂等或旧任务保护。

### 验证方式和最少交付物

- Web/API默认在本地固定干净源码与独立输出执行必要测试、编译和打包，不并发堆叠高内存任务。后端先读build.gradle再经现有编排入口串行执行；保留必要事务回归、依赖完整性、分层检查和fresh JAR。
- Runtime使用固定候选与既有测试/制品入口；测试安装在获准的隔离环境进行，不替换正在服务的生产Runtime。测试/构建、安装、健康与业务验收分别留证；默认不启动Flow。
- 真正的业务链路使用真实服务与安装包；失败/断线场景可注入故障，但不能用伪造成功回执替代实际消费者。需要外部付费调用才能证明的业务能力，须有相应授权并单独记录；未测不能写通过。
- 交付只保留：组件代码/精确commit-tree、可访问的验收环境、真实本地测试/构建批次及制品摘要证据、下方验收结果。证据沿现有handoff归档，不新增管理台账或长篇报告体系。

UX审视发现的确认对象不清、收起丢草稿、Tab顺序、重复标题、辅助字可读性，随Web实现定向修正；保持原型结构和操作路径，不单开原型重设计阶段。
