# CYF Workspace Guidance

This repository is a multi-module workspace with a Vue frontend under `web/`, Java/Gradle backend modules under `api/`, and project notes under `docs/`.

## Read First

- For a compact project map, read `docs/codex-project-map.md`.
- For multi-repository SDD delivery, read `docs/sdd-workflow.md`; use `docs/knowledge-base/` for current-state reverse-engineering reference.
- For Juyi Hall work, read `docs/juyiting-runbook.md` first, then use `docs/juyiting-feature-guide.md` for deeper flow details.
- Prefer targeted `rg` searches over broad file reads.

## Fast Iteration Principle

- 快速迭代阶段不以稳定为首要目标；一切优先往前推进。有问题就继续修问题，修不了就优化技术栈，不做保守回退作为默认选择。
- 按用户 2026-09-12 最新指令：不创建独立 Reviewer。责任 Owner 自检后合入组件 develop，由云效执行相关测试、构建、同 Run 制品发布与健康核验；不把历史审查队列作为前置条件。

## Availability-First Performance Policy（2026-09-13 用户最新指令）

- 性能超标只记录慢请求、耗时和优化待办，不得仅因 1s/2.5s/3s/5s SLO、剩余预算不足或首帧慢而拒绝、跳过下一步、取消请求或中断流。
- 保留真实网络错误处理、明确配置的传输超时、用户取消、身份切换取消、鉴权、幂等、事务和锁归属；不得把“继续等待”实现成绕过锁或伪报成功。
- 不向下游传播会被强制执行的性能 deadline，不把失败加速当成功率提升。不以更大的任意数值替换旧门槛。
- 后续优化以真实慢请求及证据排序；性能目标与实际可用性分开报告。详见 `specs/api-performance-3s-slo/spec.md` 最新修订。

## Gate Evidence Policy（2026-09-13 用户指令）

- 去掉没有依据的检查；后续遇到实际问题、形成证据后再增加，不以历史脚本或文档中的固定值作为依据。
- 发布不设置未测算的磁盘/内存预留、包大小上限或本地等待超时门槛；空间只按实际制品与回退副本计算，资源指标保留观测。
- 保留用户明确要求的云端测试、同 Run 制品绑定，以及版本/权限/进程归属、实际健康、发布互斥和可恢复安装。互斥采用等待，不抢占、不操作其他任务进程；取消由 Flow 作业控制。
- 新增硬门禁必须记录实际问题、证据、最小检查范围；涉及数值必须给出推导。详见 `docs/aliyun-flow-gate-policy.md`。

## Develop Auto-Release Policy（2026-09-12 用户指令）

- 普通功能具备上线条件后合入组件仓库 `develop`，由 Flow 自动测试、构建、上传同 Run 制品并部署；成功发布，失败停止。日常发布不逐次等待 Reviewer、人工审批或短期 ticket，也不要求先发 CI-only 再重建生产。
- 前后端正式构建与测试都在云端，本机仅轻量静态检查、开发预览和控制面操作。
- 身份/ACL、事务、迁移等风险仍由责任 Owner 明确自检并补云端回归；取消独立 Reviewer 不等于取消身份隔离、事务正确性或生产/付费授权。授权范围外的生产数据、扣费和临时操作仍须用户明确授权。

## Lightweight Gate Policy

- **L0（无需门禁）**：只读查询、状态核验、文档说明、候选配置生成、本地静态检查。主 Agent 直接执行并汇报，不创建 Reviewer/等待线程。
- **L1（自检后直接执行）**：可逆且不产生运行时副作用的配置写入，例如保存 Flow YAML 但不启动 Run、调整非生产开关、创建草稿。要求保存前值、固定候选哈希、单次写入、readback；失败先记录精确错误，不做盲目重试。无需独立 Reviewer。
- **L2（自检合入）**：普通前后端代码、测试和非关键集成。Writer 完成最小相关自检后直接合入 develop，云效在同一次发布 Run 内执行正式测试与构建；不创建独立 Reviewer，不强制重复 CI-only。
- **L3（风险与授权校验）**：身份/ACL、事务、迁移、生产数据和流水线外操作由责任 Owner 核对风险、精确目标、授权及恢复措施，不另起 release_guard/Reviewer。普通已授权 develop 发布按流水线自动校验推进；不得推导未授权扣费、生产 DML 或 foreign 进程操作权限。
- 不创建、等待或轮询独立 Reviewer；仅真实测试/构建失败、目标与制品不匹配、必要授权缺失或资源互斥可以阻止对应执行。
- Flow 特例：`UpdatePipeline` 且明确不调用 `StartPipelineRun` 属于 L1；云端构建但无部署属于 L2；普通 develop 自动发布沿用已确定的流水线自动校验，不再附加逐次 L3 审批。


## Temporary Local Release Authorization（2026-09-17 用户最新指令）

- 云效暂不可用期间，允许本地相关测试、生产构建和部署；先自检合入组件 `develop`，达到上线条件后从验证过的 exact SHA 创建冻结的 `release/<version>` 分支发布。此例外覆盖下文云端专属规定，直至用户恢复云效。
- 不跳过测试，不伪造 Flow 成功或 Run；记录 `build_origin=local_user_authorized`、前后端 commit/tree、测试及制品 SHA-256。Gradle 仍经 orchestrator 串行运行。
- 保留权限隔离、实际健康、进程归属、发布互斥、可恢复安装及生产数据/付费操作授权边界；不覆盖其他任务或已有 release 分支。详见 `docs/implementation/V1_6_LOCAL_RELEASE_PLAN_20260917.md`。

## Versioned Release Schedule（2026-09-14 用户指令）

- 后端：北京时间 06:00（含）至 24:00（不含）的 develop 自动 Run 只测试/构建和产出同 Run 制品，不自动部署；每天 00:00 汇总待发布提交，满足既有云端测试、同 Run 制品、发布互斥与实际健康条件时仅发布一次。
- 前端：patch 和 minor 增长不足两个版本号的变更可立即发布；相对当前线上版本 major 增长或 minor 至少增长 2 的为大版本，固定在每天 00:30 发布。`1.0.x → 1.2.0` 属于大版本；版本未知只记录，不得拒绝或取消发布。
- 时区为 Asia/Shanghai；只复用 `5260799` 与 `4403172`，不新增重复流水线，不抢占或取消其他 Flow Run。详细定义见 `docs/aliyun-flow-release-scheduling.md`。

### Pipeline Reuse Policy（2026-09-13 用户指令）

- 日常只使用 `5260799 / cyf-api-release` 和 `4403172 / cyf-web-release`；CI-only 可选，不新增重复发布链路。
- 临时安装、预检、排障复用 `5264702 / cyf-ops-manual`，默认手动、只读；不因每次诊断、候选哈希变化或失败重试创建新的 `cyf-output-*` 流水线。
- 运维入口由当前操作 Owner 串行使用：先核对无活动 Run，再保存前值、更新固定候选并 readback；正在运行时等待，不覆盖配置、不取消其他任务。安装、服务操作、数据变更仍按原授权范围执行；入口复用不等于自动获得授权。
- 新增独立流水线仅在确有不同长期用途且用户明确授权时执行。具体清单与本次收敛记录见 `docs/aliyun-flow-cicd-strategy.md`。

- The authoritative CI/CD policy is `docs/aliyun-flow-cicd-strategy.md`. Formal frontend and backend tests, production builds, artifact creation, and deployments run in Alibaba Cloud Flow.
- Backend production pipeline: `5260799` (`cyf-api-kit-ci`, `develop`). Frontend production pipeline: `4403172` (`cyf-web-kit`, `develop`). Both pipelines now configure develop push automatic release; webhook delivery and deployment success must still be reported from actual runs. Check `docs/aliyun-flow-develop-auto-status.json`, and always bind conclusions to the exact remote commit and Flow Run.
- Do not run local Gradle or Vite production builds by default, and do not fall back to local source-to-production scripts when Flow fails. Local success is not release evidence.
- Local frontend dev server is allowed for interactive development: `cd web && npm run dev -- --host 0.0.0.0`. Targeted local static/unit checks are allowed only when they are materially cheaper than a build and do not replace Flow verification.
- If an explicitly authorized diagnostic requires Gradle, inspect the nearest `build.gradle` first and invoke it only through `python3 ops/orchestration/cyf_orchestrator.py gradle ...`.
