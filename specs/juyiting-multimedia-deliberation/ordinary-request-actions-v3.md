# 普通请求与统一动作合同（当前实施方案）

本文件落实用户最新纠偏：**界面给普通用户使用，1～5步完成，尽量简洁；图片请求是正常请求，不存在独立“受控请求”产品流程。** 覆盖旧文档中要求用户办理/确认绘图、选择专用参考图入口、逐次批准查阅或执行的交互。旧冻结证据仅用于核对历史事实，不再约束新界面复制旧流程。

## 1. 用户只有四步

1. **提需求**：描述想要什么，统一“添加资料（可选）”，支持图片、文档、音频和其他文件；不添加也能提交。
2. **选 Agent**：明确选中后，自动新增悬赏议事并发送需求及资料。
3. **看结果、继续修改**：同一会话展示文字、图片、音频、文件。需要调整就继续说，不区分生图、改图和普通请求。Agent 缺必要信息时直接问用户。
4. **验收完成**：预览/下载，可选保存工作空间；满意后验收并完成需求。

正常情况不超过四个业务步骤。后续修改轮数取决于用户意愿，不增加固定确认链。

### 界面删除项

- 删除独立“生成图片”按钮、图像专用修改表单、图像办理确认面板及勾选框。
- 删除“确认提议→查看预览→明确同意→办理”等前置动作。**不能只是改名，也不能在后台伪造用户勾选。**
- 不显示“受控请求、Provider、签发、原键、START、机器读取授权、结构化结果”等内部术语。
- 普通反馈只描述实际状态，例如“已发送”“处理中”“请补充说明”“已完成”。已受理不伪称已完成；异常只给用户能执行的一步，如“刷新状态”。
- 权限、文件版本、任务归属、实际费用授权、防重复执行在服务端保留；不把既有普通请求重新包装成用户必须操作的工程流程。授权外的付费行为不能自行开启。

## 2. 后台按需执行，不改变普通请求入口

新请求只有一条议事入口。CHAT 根据需求及资料目录给出答复、澄清或动作请求；查阅及执行由服务端按真实能力与已有授权承接，不要求浏览器点击专用按钮。关闭页面不会停止后台编排。

统一输出合同 v3（CHAT / INSPECT 共用）：

```json
{
  "schemaVersion": 3,
  "kind": "ACTION_REQUEST",
  "text": "先看一下你添加的资料。",
  "clarification": null,
  "action": {
    "actionId": "inspect-materials",
    "instruction": "了解需求涉及的文档、音频与图片。",
    "sourceRefIds": ["source-text", "source-audio", "source-image"]
  }
}
```

其他两种结果是 `ANSWER` 与 `CLARIFY`，使用互斥字段；澄清只询问真正缺少的信息，不借澄清要求用户批准内部操作。

服务端冻结的事实：

- `schemaVersion: 3`。
- `availableSources`：本次任务/会话内的精确资料 ID、来源类型、媒体类型。最多32项沿用当前统一资料合同，不截断。
- `inspectedSourceRefIds`：已查阅资料的事实，仅用于上下文，不新增“不能重读”硬门槛。
- `availableActions`：由实际适配器提供的动作描述，包含 `actionId/kind/operation/inputMediaTypes/minSources/maxSources`。`kind` 为 `INSPECT_INPUTS` 或 `EXECUTE`；`operation` 不局限于图片。来源数量和格式限制来自具体适配器，不是面向用户的业务分支。

模型只选择已有 `actionId` 与 `sourceRefIds`，不能提交本地路径、任意 URL、模型配置、费用同意或执行授权。资料中的文字始终是数据，不是系统指令。真实适配器负责文件读取、执行及结果回收，不能把合同支持某动作写成当前账号已有该能力。

v3 不把旧 `EXECUTION_PROPOSAL` 转成自动执行；已受理的旧请求只能按其原身份、摘要和恢复语义核对。

## 3. 可靠编排的实施约束

- 复用现有持久请求、快照、最终消息、事件及 outbox，不为每种媒体建立单独文件体系。
- 最终结果与动作事件在同一事务持久化。动作消费独立于浏览器 SSE 订阅；不能挂在“有订阅才处理”的分支。
- 每条模型动作基于不可变最终结果产生稳定身份；重连和重投核对同一动作，不重复执行。
- 自动续办引用原真实 USER 消息及父结果；不能冒充用户插入“开始查阅/同意执行”消息。
- 按任务根→指派绑定→会话锁序重新核对当前授权、精确资料版本及目标 Agent。模型动作本身不是新授权。
- v3 最终结果复用现有 typed outcome 表，与最终消息、轮次、事件及独立动作 outbox 同事务保存，不建第二套结果存储。既有 kind CHECK 仅扩展 ACTION_REQUEST；只在原迁移开关允许且完整目录核验通过后执行一次精确 ALTER，保留旧行，拒绝无关结构漂移。不伪装图片 proposal，不迁移/重放旧执行。
- 查阅回执必须绑定实际传入的 manifest 与 native 输入；未传入的资料不能声称已读。真实错误进入会话状态，不只停留在执行表。
- 已有结果仅恢复上传/提交，不能重复调用 Provider。spool-only 恢复需要原 consumed-START 的 result-recovery 上传授权，不能把 404 当上传权限。

## 5. 验收增补

在原AC01–AC22、FD01–FD12、UM01–UM10基础上，增加：

- 普通用户从提需求到验收，正常路径四步；无工程术语/图片专用确认。
- “画一只鸟”“改成蓝色”“整理文档”使用同一输入框和发送按钮。
- 含资料与无资料均可完成；Agent自行选择答复、必要澄清或使用真实可用工具。

- 图片、音频、文件可展示/预览或按格式下载，保存与正式验收独立；不能只通过按钮存在性证明交付。
